## 二、产品依赖

### 结论：**产品零第三方运行时包。**

阶段五内置 Unicode Unihan 17.0.0 的离线 `kMandarin` 读音派生表；它是第三方数据资源，来源与许可如下，不属于运行时 `PackageReference`：

- 官方原件：`https://www.unicode.org/Public/17.0.0/ucd/Unihan.zip`，SHA-256 `F7A48B2B545ACFAA77B2D607AE28747404CE02BAEFEE16396C5D2D7A8EF34B5E`。
- 派生文件：`src/GlassDesk.AppServices/Resources/unihan-mandarin-17.txt`，44,348 条，SHA-256 `1557CF8D690DF2AD71461842B55AD87523E8DC2C32A903CF88990A5AE6DA268E`。
- 生成命令：`& .\tools\generate-unihan.ps1`。脚本先校验原件哈希，只选取 `kMandarin`，保留每字第一读音并去声调；多音字由用户搜索别名修正。索引运行时离线建立，不联网，不把派生字段写回 `apps.json`。
- 许可：[Unicode License V3](https://www.unicode.org/license.txt)，副本在 `docs/third-party/unicode-license-v3.txt`，发布目录另附 `UNICODE-LICENSE.txt`。许可允许复制和分发数据，并要求随数据保留版权与许可声明。

`src/` 下八个工程**没有任何 `PackageReference`**。这一点是刻意的：

- 计划书要求「第三方依赖优先选择允许闭源商用的许可证」，并「记录版本、来源和必要声明」。
- 依赖为零时，声明清单为空，许可风险面最小，也不会因为上游改许可证而被迫返工。
- 参考实现原先依赖的三个原生模块（`uiohook-napi`、`ym-fullscreen-detector`、`sharp`、`extract-file-icon`）在本产品中**没有任何对应物**：鼠标侧键、全屏检测、图标提取全部改用 Windows 官方 API 自行实现，因此不再需要 node-gyp、预编译原生产物或 Electron 运行时。

产品实际使用的全部框架与库：

| 组件 | 来源 | 许可 | 用法 |
|---|---|---|---|
| .NET 基类库 | 微软 | MIT | 全部基础功能；PNG 的 deflate 流用 `System.IO.Compression.ZLibStream` |
| WPF（`Microsoft.WindowsDesktop.App`） | [dotnet/wpf](https://github.com/dotnet/wpf) | MIT | 窗口、渲染、布局 |
| `System.Text.Json` | 微软 | MIT | 配置与应用库序列化（含源生成） |
| Win32 API 调用 | Windows 系统组件 | 系统自带 | 由本工程 `Interop/` 手写声明 |

Win32 调用为**本工程自行编写的 P/Invoke 与 COM 接口声明**，不是复制的第三方封装库。涉及：
`dwmapi.dll`（背景材质、圆角、深色模式）、`shell32.dll`（`Shell_NotifyIcon`、`SHGetKnownFolderPath`、
`ShellExecuteEx`、`SHGetFileInfo`、`ExtractIconEx`、`SHCreateItemFromParsingName`、`SHGetNameFromIDList`、`ILFree`、`SHAppBarMessage`、`SHQueryUserNotificationState`）、
`ole32.dll`（`CoCreateInstance`、`CoTaskMemFree`）、
`gdi32.dll` 与 `user32.dll`（位图转图标、读回位图像素、窗口枚举与激活、`DestroyIcon`）、
`kernel32.dll`（附加父控制台、线程 id、打开进程与查映像路径、进程 id、`CloseHandle`）、
`ntdll.dll`（`RtlGetVersion`）。

COM 接口（`IShellLink`、`IPersistFile`、`IShellItemImageFactory`）按 Windows SDK 头文件里的
IID 与方法顺序自行声明，用源生成的 COM 互操作（`[GeneratedComInterface]`）而不是
`[ComImport]`，因此进程不需要启用内置 COM 互操作，也不依赖类型库。

## 七、核查方式

本记录中的关键结论都可由命令复核，不是书面断言。

> **核查命令必须排除 `obj/` 与 `bin/`。** 阶段 3 发现原来的几条命令匹配的是 NuGet 生成的
> `obj/project.assets.json` 与 `obj/**/*.GlobalUsings.g.cs`，前者天然含
> `"projectStyle": "PackageReference"`，后者天然含 `global using System.Net.Http;`。
> 结果是命令**永远有输出**——它证明不了任何事，却看起来像一条通过的检查。
> 下面每条都用 `--exclude-dir` 排除构建产物，并写明预期结果（`grep` 退出码 1 表示无匹配，即通过）。

**产品无第三方依赖**（预期：无输出，退出码 1）：
```bash
grep -rn "PackageReference" independent/src/ \
    --include="*.csproj" --include="*.props" --exclude-dir=obj --exclude-dir=bin
```

**产品代码不调用网络**（预期：无输出，退出码 1。计划书要求搜索与排序全部本机运行、无遥测）：
```bash
grep -rn -E "HttpClient|WebRequest|WebClient|System\.Net\.(Http|Sockets|NetworkInformation)" \
    independent/src/ --include="*.cs" --exclude-dir=obj --exclude-dir=bin
```

**产品代码不启动子进程去做事**（预期：只命中 AppHost 打开数据文件夹那一处便利功能）：
```bash
grep -rn "Process.Start" independent/src/ --include="*.cs" --exclude-dir=obj --exclude-dir=bin
```
参考实现每 2.5 秒启动一次 PowerShell 做全屏检测，基线报告把它列为空闲 CPU 开销的主要来源。
本产品的产品代码路径里没有这种用法；唯一一处 `Process.Start` 是「打开数据文件夹」这条
用户主动触发的便利功能，走的是外壳。

**测试依赖版本与工程一致**：
```bash
grep -A3 "PackageVersion" independent/Directory.Packages.props
```

**测试依赖的上游仓库**：
```bash
grep -o -E '<repository[^>]*>' ~/.nuget/packages/xunit/2.9.3/*.nuspec
```

**工程不引用参考产品源码**（预期：只命中注释与自检中的只读探测）：
```bash
grep -rn -i -e "MacDock" -e "ym-launcher" -e "labwhiz" -e "zmy-devs" \
    independent/src/ independent/tests/ --include="*.cs" --exclude-dir=obj --exclude-dir=bin
```
阶段 3 复核结果：**8 处命中，全部在注释里；唯一有代码的是 `SelfTest` 里只做
`Directory.Exists` 探测**并与本产品目录比对是否重叠的那一段——正是计划书要求的隔离检查。

**产品数据目录与参考产品无重叠**：
```bash
independent/src/GlassDesk.App/bin/Release/net10.0-windows/GlassDesk.exe --selftest
# 「与参考产品目录重叠：否」
```

**产品源码里没有被复制进来的参考实现素材**（预期：无输出，退出码 1）：
```bash
find independent/src -type f \( -name "*.ico" -o -name "*.png" -o -name "*.svg" -o -name "*.ttf" \) \
    | grep -v "/obj/\|/bin/"
```
图标由代码在运行时绘制，或从用户机器上的应用文件里提取，因此源码树里没有任何图像资产。
