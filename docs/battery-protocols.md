# Peripheral battery compatibility

The status bar exposes seven selectable metrics, at most three. Peripheral providers use exact model/collection matches and expose battery telemetry only. Some upstream battery protocols require transient telemetry-session handshakes, documented below. A supported protocol is not a guarantee that every model or firmware of its brand works.

## Sources and coverage

* BatteryMonitor, MIT, https://github.com/JKWTCN/BatteryMonitor at `50f628c1ae1ced004e9fa03737cee9d6a561d80e`: model constants and query formats for Logitech HID++, Razer, ASUS ROG/TUF, AULA/AJAZZ and VGN/VXE/ATK-related keyboard and mouse chip families. The `320F:5055/5088` Weisheng protocol includes the ATK V75X hardware family; product names may differ between OEMs. VgnRy protocols requiring a mode-changing initialization are deliberately not used.
* mchose-tray, MIT, https://github.com/LORQAQ/mchose-tray at `a40465a130ed9b33f61ae1283c6cdbb08b7267c7`: MCHOSE 0x11/0x06 query, XOR decoding, command echo checks and rejection of all-zero replies.
* rapoo-tray, MIT, https://github.com/Iris-0109/rapoo-tray at `20ff56a96b94e7acfcb43f53851c5daa75aa73e0`: VT second-generation passive battery report interpretation. Office receivers are not treated as compatible by vendor ID alone.
* Windows device properties and Bluetooth SIG Battery Service 180F/2A19: only connected Bluetooth endpoints are allowed to supply percentages. Undocumented Windows compatibility battery properties may be unavailable. Physical container IDs, not names, associate nodes.
* iKF V11 Pro 2.0 / Pro⁺, converted self-developed firmware, `38B1:3419`, interface4, pageFF00/usage1, input/output64: independently implemented connection/battery getter framing and response validation from local captures and the official protocol behavior at https://hub.ikeepfun.com/assets/index-CjMBPDMB.js (2026-11-06). No vendor JavaScript or driver binary is bundled. Other iKF model IDs and the old `3412` firmware are not enabled by this adapter. Both the receiver and headset firmware must support the new protocol.
* MCHOSE V9 PRO `291D:385D`, pageFF90/usage1, input/output64: independently implemented the documented `55 65 01` battery getter after a local90% response. Research lead: https://github.com/wushuai0802/myfinder-device-battery/blob/main/engine/research/p2-protocols.md (read2026-11-06); cross-checked protocol facts against https://github.com/rafagfran/mchose-v9-pro-battery-tray#protocolo and https://github.com/PyFlat/Device-Battery-Info/blob/main/src/DeviceBatteryInfo/Sources/Mchose/MchoseProtocol.cs. This native adapter does not copy the reference implementation; the separate full reader component described below bundles upstream under its own license. Only the verified V9 PRO identity is enabled, not V9 Turbo/Turbo+ or lighting interfaces. Source links are mutable; local raw response and exact wire facts are recorded in docs/superpowers/plans/mchose-v9-battery-investigation.md.
* HeadsetControl 4.2.0, https://github.com/Sapd/HeadsetControl/tree/4.2.0 (commit `91ee690a5e302a10a6f4f75a46be05846a38a3b0`): independent GPL-3.0 executable with its source archive, license and HIDAPI dependency source/license in components/headsetcontrol. JSON mode enables multiple information getters; it does not change device settings. The main project contains only JSON/process integration, not GPL implementation code.

MIT attribution texts are in docs/third-party/peripheral-battery and copied to distribution notices. Native model rows remain labelled upstream-adapted, not locally verified. HeadsetControl supports only its version-pinned Windows matrix; a supported brand does not imply every headset is supported.

## Full MyFinder reader integration, 2026-11-07

MyFinder Device Battery1.3.9 is pinned to `bbcb779be4633ecf9183f53409de118dc9cb1fd6`. All44 mouse/headset/keyboard target entries in its compatibility catalog are mapped in `components-src/battery-engine/coverage.json`: 41 original Python readers, two ported native profiles and the existing Windows/BLE Bluetooth path. Controller-only readers are excluded. This includes standard HID, dynamic Logitech HID++ slots, MCHOSE headset/keyboard families, Razer, Audeze, ASUS, HyperX, SteelSeries, Corsair, Keychron, Lofree, VGN and the remaining catalog readers. This number counts reader entries, not individual device models.

The separate `components/battery-engine` process contains the AGPL-3.0-only upstream readers with original MIT notices and a private CPython/HIDAPI runtime. Its complete upstream source, bridge/native-profile sources/tests, Python and HIDAPI sources and licenses are bundled. The earlier native MCHOSE V9 adapter remains independently implemented; the additional upstream readers are distributed in this separate component. No upstream GUI, updater or control endpoint runs. The bridge disables ancillary DPI capture; Razer PA/Barracuda transient E1 telemetry sessions and native ATK's01/04 handshake are retained within the battery protocol, with best-effort session cleanup. No prior remote-session state restoration is claimed.

The host supplies current exact HID paths and physical container bindings; names and VID/PID alone never associate histories. Verified Logitech receiver slots merge into native slot keys; other logical units keep stable keys independently of sibling counts. Cached/unconfirmed percentages are unavailable, coarse values remain estimates, and unknown charging stays unknown. Native ASUS stepped batteries are marked approximate; BLE first tries Windows battery properties before the standard GATT service.

While display is active, one hidden line-based helper and its serial worker preserve provider state between polls. Device inventory changes recreate the worker; hiding/disabling battery display, sleep, cancellation, timeout or exit releases the process job. Settings discovery uses a temporary query. There is no network, system Python or installed service dependency. The trusted build lock validates all vendor/source/payload hashes before runtime execution and the package verifier requires the entire component.

Final local installation verified569 payload files, including131 locked battery component files. Existing settings were byte-identical after installation. The new host completed two real inventory queries and released its test processes. At that time the V9 receiver was absent and A7/iKF did not return valid percentages, so the prior79/50/90 readings above are historical validation, not current readings. Remaining physical acceptance includes awake-device recheck, vendor-software coexistence across other models, hotplug, sleep/wake and input behavior. Parser fixtures and successful builds do not establish those outcomes.

## Current machine validation, 2026-11-06

Read-only enumeration detected MCHOSE A7 Pro `5253:1021`, Jet75-II `41E4:211A` and iKF V11 Pro+ `38B1:3412`. The MCHOSE command returned correctly echoed but empty/all-zero decoded payloads, both through cancellable IOCTL and a separate opt-in synchronous comparison probe. These replies are rejected, so no current percentage is claimed. Jet75-II and iKF have no verified native battery adapter and display unavailable. HeadsetControl reported zero supported connected headsets on this machine. Bluetooth cached percentages from disconnected endpoints were not used.

Raw captures are local ignored artifacts; the probe prints no serial numbers, addresses or device paths. This validation does not establish battery accuracy on hardware not present, device sleep/hotplug acceptance across all models, or end-to-end FPS/memory targets.

Later on the same day, MCHOSE A7 Pro produced a valid79% reading. After the user completed receiver and phone APP-side headset conversion, iKF V11 Pro 2.0 returned50% with iKF Audio running concurrently. The integrated service preserved the headset's default audio status. iKF connection responses require the expected command and valid CRC; battery responses require a complete single packet, matching application sequence, battery property and0–100 value. ACKs and unrelated/stale responses are ignored. Charging information is left unknown because its semantics have not been verified on this firmware. The support label records this specific local validation, not general iKF compatibility.

MCHOSE V9 PRO subsequently returned90% (state02) both through an opt-in read-only probe and the integrated service, which preserved default audio=true. Status00/03 hides the potentially frozen percentage and explains external power without claiming to distinguish charging from full. Status1A is offline, not0%. These other states have fixture coverage based on upstream evidence, not local physical acceptance. The device's raw percentage is used; upstream observations of10% steps are not a claim of1% measurement resolution. Unknown states, bad lengths and unrelated reports provide no reading; handles and waits remain bounded by the existing cancellable native transport.

## Runtime limits

Queries run serially at 60-second intervals plus debounced device changes. HID operations have bounded waits and cancel/reap overlapped operations before releasing their buffers. Provider timeouts reject late results and prevent overlap with an unfinished request. HeadsetControl child queries have a 10-second deadline and terminate on cancellation. Readings older than two minutes are unavailable. Disconnects and stale values never become artificial 0% readings.

Selected item settings survive unrelated Dock edits and failed saves. Manual device bindings stay bound offline; automatic selection retains a connected choice and prefers the default audio endpoint for headsets. Receiver slots are distinct devices; generic Windows receiver placeholders are suppressed when slot readings exist.
